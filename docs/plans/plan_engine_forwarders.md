# plan_engine_forwarders.md: engine interfaces through generated native forwarders

Status: phase 1 (the IVModelInfo spike) under way on branch
`claude/engine-forwarders`, started 2026-10-13 at main 25e9c07 once phase 0
held: the current method green on Linux and Windows CI.

## 1. Why

Managed calls engine interfaces by indexing the engine object's vtable through
the structs in `src/abi/VtableLayouts.g.cs`, generated by `tools/vtable-layout`.
The engine is MSVC's on Windows and gcc/clang's on Linux, and the two C++ ABIs
order some tables differently: MSVC gives a virtual destructor one slot rather
than two, and lays each class's overloads out grouped and in reverse
declaration order. 32 of the 159 layouts differ.

The current fix (commits 1ef3e35, 94e1e55, 872cf4a) keeps that knowledge in
managed: a layout MSVC orders differently is read through properties that pick
the Windows index on Windows (`[VtableSlot(itanium, microsoft)]`,
`MicrosoftEntries`, `VtableAbi`), `Vtable.EntriesFor<T>()` holds native's count
against the ABI's own length, `ManagedVtableGenerator` writes the Steam
callback's thunks at the Windows slots, and slots returning a class by value
are `[MemberFunction]`. It works, and call sites are unchanged, but managed has
to know both ABIs.

The ask (2026-10-13): move that from a runtime choice in managed to a
compile-time shim in native code, so managed is as simple as it can be.

## 2. The idea

The C++ compiler already knows the layout: `obj->GetMass()` compiles to the
right slot on whichever ABI it is built with. So for every engine method
managed calls, generate a one-line native forwarder and let the compiler do the
dispatch:

```cpp
// GENERATED by tools/vtable-layout, per interface, in one fixed order
static float  PhysicsObject_GetMass( IPhysicsObject *self )    { return self->GetMass(); }
static Vector PhysicsObject_GetInertia( IPhysicsObject *self ) { return self->GetInertia(); }
```

The forwarders of one interface form one table, served the way the shim areas
are: a bound interface with no virtual destructor and no overloads, which both
ABIs lay out identically (the generator already asserts that shape for shim
areas). The C# struct is generated from the same walk in the same order, with
plain fields.

`self->Method()` still dispatches through the object's own vtable, so a derived
class's override is what runs, exactly as now.

## 3. What managed loses

- the property form, `[VtableSlot]`, `VtableAbi`, `MicrosoftEntries` and
  `Vtable.EntriesFor` (one layout everywhere, fixed order, no destructor slots);
- `[MemberFunction]`: a forwarder is a free function, so a `Vector` return is
  the platform's ordinary convention on both;
- every read of an engine object's vptr. The 70 sites that do
  `(*(PhysicsObjectVtbl**)obj)->GetMass(obj)` (60 of them vphysics objects:
  `PhysicsObjectVtbl` 31, `PhysicsEnvironmentVtbl` 13, ...) become calls
  through the interface's forwarder table, passing the object;
- the `Refused_` slots managed cannot spell (varargs, a class by value): a
  forwarder takes marshalable parameters instead, so `PROXIES` in
  `tools/vtable-layout` folds into the generator.

And header drift becomes a COMPILE error: a signature that changes in a header
stops the generated forwarder compiling on that platform, where today it shows
up as a count mismatch at bind time or in vtable_index_agreement_test.

## 4. Where the forwarders live: their own native libraries

User suggestion (2026-10-13): native interop libraries per interface type,
not code in server/client.

The forwarders are stateless pure functions over a `self` they are handed.
They need the SDK headers to compile and nothing at run time: no engine
connection, no tier0 state, no globals. That makes them a good fit for
libraries of their own, on the pattern `libss_particles.so` already set
(`src/client/native/particles_lib/`, `plan_particles_so.md`): one shared
object per family, exporting `CreateInterface` and nothing else, answering
version strings with forwarder tables.

Candidate families (to settle in phase 1):

| library (Linux / Windows)                       | serves |
|---|---|
| `libss_fwd_engine.so` / `ss_fwd_engine.dll`     | the factory interfaces: model info, filesystem, cvar, engine client/server, render view, sound, trace, spatial partition, string tables, ... |
| `libss_fwd_vphysics.so` / `ss_fwd_vphysics.dll` | vphysics' interfaces and its per-object tables (environment, object, shadow/motion/player controllers, friction snapshot, constraints, springs, key parser) |
| `libss_fwd_steam.so` / `ss_fwd_steam.dll`       | the Steam callback object (section 6) |

Why split: server.so and client.so keep only what the engine requires of them;
each library's test pins its export set (as `particles_lib_isolation_test`
does); a family can be added or rebuilt without touching the game DLLs; and the
shim line ratchet sees the forwarders as their own row rather than growth of
the shell.

Open: who loads them. Either the shell (client.so/server.so `dlopen`s them
beside itself, as client.so loads libss_particles.so) and serves their tables
through the internal factory, or managed loads them itself with
`NativeLibrary.Load` and calls `CreateInterface`. The second keeps the game
DLLs out of it entirely; the first keeps one route for every native interface.

## 5. The checks

- Count and hash at bind, as managed-built tables already do: the generator
  writes a per-slot hash (FNV-1a over the forwarder's signature, as
  `[SlotHash]`) into both the C++ table and the C# struct, and the bind refuses
  on any difference, naming the slot.
- Each library's export set pinned by a native test (CreateInterface only).
- `vtable_index_agreement_test` shrinks to what still reads a vtable by layout
  (the shim areas, the managed-built areas, and whatever section 6 leaves).
- Generated files are committed, as `VtableLayouts.g.cs` is, and
  `tools/vtable-layout` (the check) fails when they are stale.
- The generated C++ calls Valve methods through SDK headers, so it starts with
  `tools/valve-header.txt` and gets a row in `docs/valve-header-new.tsv`.

## 6. The other direction: Steam callbacks (and maybe vphysics callbacks)

`CCallbackBase` is a Valve class managed implements (`SteamCallbackVtbl`,
valve-implemented-by-managed), and MSVC reverses its two `Run` overloads. A
native class deriving `CCallbackBase` whose three virtuals forward to a
managed table in fixed order removes that from managed too; the native object
is created and released through the Steam forwarder library, one per
registered callback, released when managed releases it (no accumulation across
runs).

The vphysics callbacks (`IPhysicsCollisionEvent` and the rest) lay out the
same on both ABIs, so they need nothing; moving them too would be for
uniformity only. Decide in phase 5.

## 7. Costs

- One extra direct call per engine call (forwarder, then the virtual call that
  already happens). The hot vphysics reads keep `[SuppressGCTransition]`.
  Measure the physics frame and the live-gate stages
  (`tools/live-gate-budget.tsv`) before and after; "move first, measure after".
- More C++, all of it generated: one line per method managed calls (about 200
  distinct methods today, not the 1,239 typed slots), plus a CMake target per
  library. This partly reverses the earlier ruling that managed calls engine
  vtables directly; the user asked for it.
- A mechanical migration of the 70 per-object sites and the bound impl
  classes (`_vtbl->X(_self)` becomes `_fwd->X(_self)`).

## 8. Phases

0. **The current method green on CI, Linux and Windows** (prerequisite, per
   the ruling). Nothing below starts before it.
1. **Spike, one interface end to end**: `IVModelInfo` (a destructor and two
   overload pairs, so both MSVC rules are exercised). Generator emits its
   forwarders and C# struct; `libss_fwd_engine` builds on both platforms;
   managed binds with the count/hash check; the managed facts pass on both.
   Settle the library split and who loads them (section 4). Measure one hot
   call against the direct-vtable path.
2. **The factory interfaces**: every called-by-managed engine interface moves;
   the impl classes switch; `PROXIES` folds in.
3. **vphysics**: `libss_fwd_vphysics`, then the 60 per-object sites.
4. **The rest of the per-object sites** (string tables, net channel info).
5. **Steam callbacks** (section 6); decide on the vphysics callbacks.
6. **Delete**: the property form, `[VtableSlot]`, `VtableAbi`,
   `MicrosoftEntries`, `Vtable.EntriesFor`, `[MemberFunction]`, the
   generator's Microsoft numbering (`microsoft_slots`) where nothing reads it,
   and the agreement test's Windows arms that no longer have a subject.
7. **Packaging and CI**: the libraries in both archives
   (`tools/package-release`'s native lists) and in the CI smoke checks.

Each phase lands green on both CI jobs before the next starts.

## 8a. Phase 1, as built (2026-10-13, branch claude/engine-forwarders)

What the spike settled, so later phases follow it rather than re-deciding:

- **The generator** is `tools/engine-forwarders`, beside `tools/vtable-layout`
  and reusing its header walk (`derive_chain`, `signature_of`, `slot_hash`).
  It runs from the farm, as vtable-layout does, and writes
  `src/fwd/native/fwd_engine.g.inc` and `src/abi/EngineForwarders.g.cs`.
  `FORWARD` lists, per interface, the methods managed calls by the field
  names `VtableLayouts.g.cs` gives them (an overload's second is `Name_2`);
  the table is in header declaration order whatever order the list has.
  A routine row in `tools/checks.tsv` runs its self-test and its staleness
  check.
- **The table** is a plain struct, not a C++ vtable: `SSForwarderTable`
  (`src/fwd/native/ss_fwd.h`) is the slot array, a hash per slot and the
  count. Its first word is the slot array, so the internal factory can hand
  it out as an object like any other. The forwarders take the ENGINE object
  first; managed calls `_fwd->GetModel(_self, index)`.
- **The library** is `libss_fwd_engine.so` / `ss_fwd_engine.dll` in
  `src/fwd/native` (mapped into the farm as `sourcesharp/fwd`, shim letter
  b). It links no SDK library. **It exports `SSFwdEngine_Table`, not
  `CreateInterface`** (section 4 said CreateInterface): the game DLLs export
  CreateInterface themselves, and a second one in a library they need would
  be one more symbol for the engine's lookup to resolve against.
- **Who loads it (section 4's open question): the game DLLs.** server.so
  and client.so link it as client.so links libss_particles (DT_NEEDED,
  RUNPATH $ORIGIN; the import library on Windows), and
  `SourceSharp_InternalFactory` serves every `SSFwd_<table>` name through
  `SSFwdEngine_Serve`. Managed has no path to a native library of its own
  (it never loads one; only the launcher builds a `bin/<platform>` path), so
  this is the route that already works, on both sides, unchanged.
- **The engine object** is still acquired from the engine's factory by
  version string, but as a pointer only: its vtable length is not held
  against anything, because managed never indexes it. The object is asked
  for before the table, so a side that does not serve the name says so by
  that name.
- **The check at bind** is count, then every slot's hash
  (`Forwarders.TryBind`), naming the slot that differs.

**The measurement** (one hot call, from managed, the path the game takes):
`GetModelType` through the engine object's vtable slot against through its
forwarder, 50M calls a round, 5 rounds, release build of the scratch
harness, on the 4-core Xeon @ 2.10 GHz this ran on:

| | vtable | forwarder | difference |
|---|---|---|---|
| ns per call, 5 rounds | 2.18 - 2.72 | 2.91 - 3.28 | +0.49 to +1.05 |

So about +0.5 to +1 ns a call: one extra direct call and return. IVModelInfo
is asked a handful of times per model load, not per frame; the per-frame
cost question belongs to phase 3 (vphysics), which measures the physics
frame before and after as section 7 says.

**Windows, proven in CI at 135af5f:** `ss_fwd_engine.dll` builds and
server.dll and client.dll link it; `fwd_engine_test` passes under MSVC (213 of
213 native tests); the managed facts pass in both Windows tiers; and the
sniper build's GLIBC ceiling holds for `libss_fwd_engine.so`. Phase 1 owes
nothing further.

## 9. Done when

- No managed code reads an engine object's vptr or knows which ABI it runs on.
- Every engine call managed makes goes through a generated forwarder, checked
  by count and hash at bind.
- The forwarder libraries ship in both archives, each export set pinned.
- The physics frame and live-gate stages are within budget, with the numbers
  recorded here.
