# `interpolation-stock.tsv` — where it came from

Thirty frames of the **native** `CInterpolatedVar` — `game/client/interpolatedvar.h`,
as the standalone client shell drove it through `m_iv_vecOrigin` and
`m_iv_angRotation` — recorded off a live `dm_lockdown` **before**
`plan_entity.md` step 6a changed anything about how the client interpolates. It
is the acceptance for that step:
`InterpolationTests.TheManagedRingsReproduceEveryRecordedOriginBitForBit`
replays every row through the managed rings and requires the origin it produces
to match **bit for bit**.

Recorded at `entity-port` commit `69680b72`, with `tools/6a-probe-interp.diff`
applied and nothing else of 6a written.

## Why the answers are in it

Each entity carries three things: **the history it already had** at the moment
the probe armed, **every networked sample filed for it** afterwards, and **every
`Interpolate` call made on it — with the pose the engine's own arithmetic
produced**. Feeding the first two back and comparing the third is what makes
this a comparison of managed arithmetic against the C++ it replaces, rather than
against itself. A fixture of poses generated by the code under test would agree
forever and prove nothing.

The arm state matters as much as the samples: an entity that existed before the
window has a history that cannot be reconstructed from anything inside it, so a
recording without the `AH` rows would replay from an empty ring — which is not
the state the engine was in, and the first three calls of every entity would be
compared against the wrong arm.

## The rows

| tag | what |
|---|---|
| `CV` | `cl_extrapolate_amount`, the client's interp amount, the tick interval |
| `AR` | one live entity at the moment the probe armed: handle, index, classname, whether the pass writes it |
| `AH` | one entry of that entity's history, newest first: index, the origin's change time, the angle's, both values |
| `N` | a networked sample being filed: curtime, change time, interp amount, whether it was a create, the pose, the packet timestamp |
| `I` | one `Interpolate` call: curtime, interp amount, whether extrapolation was allowed, the context timestamp, the pose going in **and the pose the engine produced** |

`%.9g` throughout, which round-trips an IEEE-754 single.

## How to record it again

    git checkout 69680b72 -- src/sourcesharp/game/client/shell_standalone_client.cpp \
                             src/sourcesharp/game/client/shell_standalone_client.h
    cp src/sourcesharp/game/client/shell_standalone_client.cpp /tmp/pristine.cpp
    cp src/sourcesharp/game/client/shell_standalone_client.h   /tmp/pristine.h
    git apply tools/6a-probe-interp.diff
    src/buildsourcesharp debug
    export DEBUG_API_DIR=/tmp/ss-debug-api-6a
    tools/6a-record-interp /tmp/raw.tsv          # 60 frames, ~11k rows
    cp /tmp/pristine.cpp src/sourcesharp/game/client/shell_standalone_client.cpp
    cp /tmp/pristine.h   src/sourcesharp/game/client/shell_standalone_client.h
    touch src/sourcesharp/game/client/shell_standalone_client.*
    tools/6a-select-interp /tmp/raw.tsv <this directory>/interpolation-stock.tsv 30

`tools/6a-select-interp` is what makes a recording into a fixture: it keeps
every entity that received a sample inside the window (the movers), six that
received none (the still ones are an arm too), each entity **whole**, and the
first thirty frames of each. It PRINTS what it kept, so a fixture that lost an
arm is visible rather than merely smaller.

The scenario drops four `prop_physics` oil drums and fires an RPG. The drums are
the point: a settling prop is networked at the update rate and drawn at the
frame rate, tumbling — so the origin steps and the **facing** steps, which is
the only way the quaternion path gets exercised at all.

## What it covers, counted

520 rows: 12 entities at the arm with 37 history entries between them, 140
samples filed, **330 `Interpolate` calls** — 660 ring reads, because each call
reads two rings.

| arm | ring reads |
|---|---|
| cubic (three samples, hermite) | 214 |
| cubic with the interval renormalised (`TimeFixup_Hermite`) | 184 |
| linear (two samples straddling the target) | 2 |
| the target is past every entry, so the newest holds | 432 |
| every entry is newer than the target, so the oldest holds | 12 |
| a create — history thrown away and reseeded (`Reset`) | 4 |
| a sample filed whose value had not changed | 83 |
| entries flushed as newer than an arriving sample | 12 |
| history trimmed as older than the target | 254 |
| two identical facings taking the slerp's equality exit | 30 |
| a slerp whose destination quaternion had to be negated | 4 |

`214 + 2 + 432 + 12 = 660`, which `EveryRingCallTookExactlyOneArm` asserts — the
arms partition the calls, so the sum is the same number reached another way.

## What it does NOT cover, and why

Stated rather than left to be discovered. Each of these is **zero** over the
whole recording, and `InterpolationTests` has a fact that says so — if a later
recording DOES reach one, that fact goes red and this table has to be rewritten.

- **Extrapolation.** `interpolatedvar.h:960` guards the arm with
  `CInterpolationContext::IsExtrapolationAllowed()`, which is false unless
  something on the stack made a `CInterpolationContext` **and** called
  `EnableExtrapolation(true)`. The standalone client's interpolation pass made
  no context, so the flag was false for **all 10,380** `Interpolate` calls in the
  raw recording. The arm is ported anyway and covered by a hermetic fact.
- **The fraction clamp**, `MIN( frac, 2.0f )`. Dead code in stock too, and
  provably: the fraction is only computed at the index where the target is at or
  past `older`, while `newer` was set because the target was before it, and the
  ring's timestamps are monotonically decreasing. The fraction is in `[0, 1)`.
- **The single-sample exit.** It needs `newer` still unset after the loop, and
  the loop sets it for every entry newer than the target. The one way through is
  the `older_change_time == 0.0f` break — an entry whose timestamp is literally
  zero, which nothing live files.
- **A ring overflow.** `InterpolationRing.Capacity` is 24 against a history that
  holds about `(interp + 0.05) × updaterate + 3` ≈ 13 entries. An overflow would
  be dropping history stock would have kept, so it is counted and asserted zero.

## Four arms the fixture could not reach, found by mutating rather than by reading

Twelve one-line mutations of `Interpolation.cs` were applied, built and run.
Eight were caught by the replay. **Four were not**, and each named a real gap:

| mutation | the replay said |
|---|---|
| `Truncate( i + 3 )` → `i + 2` | GREEN |
| `targettime < older_change_time` → `<=` | GREEN |
| the cubic's `dt2 > 0.0001f` gate removed | GREEN |
| the blend's `dt > 0.0001f` gate removed | GREEN |

Three of the four are what the algorithm does when **two samples share a
timestamp**, which a real server does not do — and the fourth is how much
history a trim leaves behind, which nothing in thirty frames of steady updates
notices. Four hermetic facts now cover them
(`ATrimLeavesThreeSamplesBehindTheTargetAndNotTwo`,
`ATargetLandingExactlyOnASampleTakesThatSampleAsTheOlderOne`,
`TwoSamplesSharingATimeAreNotACubic`,
`TwoSamplesTooCloseInTimeToDivideByHoldTheOlderOne`), and all twelve mutations
now go red.

## Angles are compared to a bound, not bit for bit

The origin is pure add-and-multiply and matches exactly. An **angle** is blended
through quaternions: `AngleQuaternion` calls `sinf`/`cosf`,
`QuaternionSlerpNoAlign` calls `acos`/`sin`, and `QuaternionAngles` ends in three
`atan2f`. Those are the platform's libm in the C++ and the runtime's in the C#,
and no amount of care in this port makes two libms agree in the last bit.

The worst disagreement over the whole fixture is **3.81e-05 degrees**, about
three ulp of a float at 90. The fact requires under `1e-4` — a real algorithmic
error moves an angle by degrees, not by millionths of one.

## The box it was recorded on

One other lane's game was running (`pgrep -c -x hl2_linux64` = 1 before, 3
after — two of those are other lanes'). That affects the frame rate and
therefore the *timings in the recording*, and not the recording's validity: every
row carries the times it ran under and the replay is fed them. It does mean the
recording ran at about 18 frames a second on a listen server, so the server
ticked once per client frame and **every one of the 278 samples was the only
sample of its frame window** — a number the design of the sample pass depends
on and which is quoted in `.claude/entity-port/status/6a.md`.
